## 一、背景与动机

### 痛点发现
- 小团队缺乏秘书，日程协作混乱
- 每个人对工作安排说法不一，无法说清楚什么时候出差、录片子、参加活动
- 市面上日程管理软件的共同问题：**每次创建日程都要填表**（点加号→填标题→选时间→选地点→选参会人...）
- 修改日程时整个流程要重走一遍

### 核心想法
> 能不能做一个像微信对话框一样的工具？你不停往里丢需求，后面有个聪明的脑袋帮你把问题捋顺，给你一个结构化的结果。

## 三、为什么其他方案不行？

| 方案            | 问题                               |
| ------------- | -------------------------------- |
| **直接用大模型**    | 有记忆窗口限制，日程多了会被切掉；无法精准定位和修改历史日程   |
| **Siri**      | 只能处理单一增删改查，无法多意图批量操作；没有费用管理能力    |
| **Web2时代产品**  | 都是填表式交互，没有大模型，只能通过表单图形界面来结构化用户意图 |
| **套壳AI产品**    | 聊天机器人和数据库高度隔离，无法无缝操作             |
| **Rabbit/龙虾** | 妥协了隐私性（需要开放所有权限）和经济性（会烧干你的头）     |

## 四、技术架构

### 4.1 产品架构 = 大模型 + Agent + 图形界面
```
┌─────────────────────────────────────┐
│           Orchestrator Agent        │  ← 编排器：跨领域协调
├─────────────────┬───────────────────┤
│  Schedule Agent │   Expense Agent   │  ← 领域Agent：独立业务处理
├─────────────────┴───────────────────┤
│         Shared Infrastructure       │  ← 共享设施
├─────────────────────────────────────┤
│              Database               │
└─────────────────────────────────────┘
```

### 4.2 薄客户端原则
- **iOS只是显示界面**，所有增删改查、Agent循环、工具调用都在后端
- iOS前端像"传菜员"，只负责将后端指令进行前端渲染
- **好处**：拓展安卓/桌面端时只需写前端界面，业务逻辑不受影响

### 4.3 混合渲染策略
- **聊天界面**：iOS原生（滑动组件、卡片选择、输入框、Photo Picker）
- **日历视图**：Web页面（通过桥接和iOS原生硬件能力结合）
- **原因**：AI写iOS代码质量太低，玄学bug多；同样的交互，Web只写一下午，iOS可能要两个月

### 4.4 DDD领域驱动设计
- 日程管理和费用管理是完全独立的业务域
- 由**编排器Agent**负责跨领域协调和查询
- **好处**：
  - 可以独立部署
  - 业务语义严格隔离
  - 高内聚、低耦合（甚至完全不耦合）

## 五、Agent架构演进

### 阶段一：意图解析器 + 脚本执行
- 大模型只做意图解析，靠代码脚本完成执行
- **问题**：丧失灵活性，脚本必须从头跑到尾，无法中途打断或调整

### 阶段二：完全ReAct循环
- Reason → Act → Reason → Act 无限循环
- **问题**：效率低，批量删除四个事件要推理四次，时间成倍增加

### 阶段三：计划与执行流水线 ✅
```
用户需求 → 生成计划（包含所有动作） → 用户确认 → 批量执行
```
- 不管用户要批量创建还是单一创建，都是"一个计划"
- 大模型统一推理、统一解析时间地点
- **效率提升**：原来批量创建5个事件要1.5-2分钟，现在大幅缩短

## 六、Smart Agent, Dumb Tools原则

### 错误做法
- 工具里加校验逻辑、解析逻辑、写入数据库逻辑
- 工具变成黑盒，bug难以定位

### 正确做法
- **Agent掌握足够上下文，做充分推理判断**
- **工具只做最愚蠢、最简单的执行**
- 重构时删掉了8000-9000行代码，把创建/删除/更改工具都变成纯执行器

## 七、工程品质

### 7.1 可观测性（约3万行代码）
- **决策ID追踪系统**：每个Agent步骤都有编号
- **快速定位bug**：像击鼓传花，第三个小朋友掉花就锁定第三个
- **Login系统**：从1万行代码时就开始建设

### 7.2 自改进飞轮
```
生产环境报错 → 查log → 自动生成测试用例 → 本地复现 → 加入回归测试
```
- 写了100+个测试用例
- 通过WebSocket投送到iOS模拟器自动跑
- **不仅验证数据结构，还能验证UI渲染**

### 7.3 为什么不能只靠AI扫代码找bug？
- Token消耗巨大，上下文爆炸
- 扫一个bug要8-10分钟
- 如此复杂的跨领域多Agent架构，时间成本不可承受

## 八、设计体系

### 8.1 Tokenized设计体系
- 字体、字号、颜色、间距、阴影、材质等全部变成设计令牌
- 通过JSON的token loader加载到每个组件
- **好处**：选一次规范，所有组件自动统一

### 8.2 工具链
- **Penpot MCP + Claude Code + Mobbin** 找灵感
- Penpot价值：可以直接让Claude在CLI中画UI，解决不能实时预览的问题

### 8.3 关于原创
- 日历界面参考了**Time Page**（App Store可搜索）
- 建议：交互方式已基本沉淀，布局直接拿来用，颜色自己做创新
- 如果产品上线收费，需要换原创界面

## 总结

这个视频展示了一个非技术背景的人，如何在48天内利用AI工具从0到1开发出一个生产级的Multi-Agent系统。核心经验：

1. **架构先行**：薄客户端 + DDD + 编排器模式
2. **Agent设计**：计划执行流水线 + Smart Agent/Dumb Tools
3. **工程品质**：可观测性 + 自动化测试 + 自改进飞轮
4. **技术选型**：关键领域一步到位，其他地方该省则省
5. **设计体系**：Token化 + 参考优秀产品 + 混合渲染
